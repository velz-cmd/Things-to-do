# Discover mechanism matrix

| User need | Correct mechanism | Required evidence | Money path | Confirmation |
| --- | --- | --- | --- | --- |
| Support a verified person | Direct support | Claimed identity and verified payout destination | Explicit managed or connected wallet to recipient | Confirmed Arc transaction and receipt |
| Reward accepted work | Work reward or program obligation | Accepted activity, attribution, active policy, payout-ready payee | Authorized settlement package | Confirmed transaction and receipt |
| Capitalize repeated community activity | Pool | Published Pool, active policy, treasury, funding terms | Explicit funder wallet to Pool mechanism | Confirmed deposit, then policy-controlled distribution |
| Establish eligibility or allocation rules | Program policy | Versioned operator decision and source requirements | No transfer during policy setup | Persisted active policy state |
| Pay for one API call, request, dataset, citation, or time unit | x402 usage payment | Provider offer, price, request, and delivery proof | Per-use payment adapter | Provider response and payment receipt |
| Claim an earned amount | Claim | Confirmed obligation or earning and payout-ready payee | Existing claim and settlement pipeline | Confirmed transaction and receipt |
| Fund a future goal without operating rules | Funding target only | Operator-created target | No transfer until a valid mechanism exists | Target remains unconfirmed |

## Selection rules

- Use direct support for a person, not a Pool with one recipient.
- Use a work reward when accepted evidence and an approved policy determine the amount.
- Use a Pool for repeated community allocation under an operating policy.
- Use x402 only for actual pay-per-use exchange. It does not replace community funding or direct support.
- Use a claim only for an existing confirmed earning or obligation.
- Never show a target or configured ledger amount as available or confirmed money.
